# Batch-size probe: Gemini 3.5 Flash Lite, citation model, two gold documents (2026-11-06)

How does the quality of a model's corrections of the citation model (`grobid.training.references`) change with the number of review units per request and with the output mode?

## Setup

```bash
python -m pte_plugin_auto_annotation.probe \
  --model google/gemini-3.5-flash-lite \
  --doc 10.12775__clr.2013.008 --doc 10.5771__2699-1284-2024-3-149 \
  --variant grobid.training.references \
  --batches units:1,units:4,units:8,units:16,units:32,units:64 --modes all,changed \
  --repeats 3 --retries 6 --concurrency 4
```

- Model: `gemini-3.5-flash-lite` through the editor's Google provider (paid tier), temperature 0.
- `10.12775__clr.2013.008`: reference = gold version `na4qn5`, input = GROBID extraction `qbb9sh`; 56 of the extraction's 64 units match a gold unit by text.
- `10.5771__2699-1284-2024-3-149`: reference = gold version `a2xyr8`, input = GROBID extraction `bfn4g7`; 52 of 70 units match.
- Rules: the machine refs of each gold version's `editorialDecl` (citation model, data correction, schema fragment), about 35K characters per prompt. The two documents point to slightly different rule versions.
- A run of the reference segmentation model on the same documents is not reported: its input versions were not the extractions (see Limits).

## Observations

- Small batches are best. One unit per request gives the highest edit F1 on both documents (about 81, in `all` mode on clr.2013.008 and in `changed` mode on 2699-1284-2024-3-149), with little spread between repetitions. From 16 units on, F1 drops to about 45–65 and varies more.
- The drop comes mostly from changed text. On clr.2013.008, the share of units whose text the model altered rises from 4% (1 unit) to 30–52% (16–32 units, `all` mode); those units are rejected by the text check and scored as the unchanged input.
- `changed` mode is as good as or better than `all` up to 8 units on 2699-1284-2024-3-149, and slightly worse on clr.2013.008. At 64 units it can collapse: on 2699-1284-2024-3-149 the model returned 12 of 156 units in all three repetitions (edit recall 8%), the "lazy model" risk of returning only changed units.
- Position in the batch shows no consistent pattern; the losses at larger sizes are spread over the whole answer.
- No retries were needed on the paid tier.
- This contradicts the run of 2026-11-05 (`gemini-flash-lite-latest`, gold version `fz3uhg`, free tier), where quality did not fall up to 32 units. The model behind the alias, the changed gold version and the different rule versions all differ between the runs, so the two reports are not directly comparable.

## Consequences for the pipeline

- With this model, batches of at most 4–8 units; split-and-retry on text changes remains necessary.
- Since about 35K characters of rules are repeated in every request, small batches need prompt caching of the rules prefix to be affordable.
- `changed` mode only with small batches, and with a check that the answer is not implausibly short.

## Limits

- Two documents, one model, three repetitions.
- The default input is the first version of the gold version's lineage (`parent_stable_id`). For older documents this lineage can be wrong: in the reference segmentation run, it led to versions that were not the extractions, which is why that run is not reported. The inputs used here were checked to be the GROBID extractions.
- Units that annotators split or merged cannot be aligned and are not scored (8 and 18 extraction units).
